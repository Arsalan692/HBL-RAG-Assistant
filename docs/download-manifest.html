The rule that makes air-gap transfers fail

Almost every tool here will happily reach for the internet at run time, not just install time — and on the workstation that is a hang or a crash, not a download. So nothing may be referenced by its online name after the transfer. Model names become local folder paths, pip installs read a local folder, and HBL_HF_OFFLINE=true stays on permanently so a library cannot quietly try.

01On the laptop

Four downloads into one staging folder. Make it anywhere convenient — the examples call it transfer\.

A · Generation models, through Ollama

Install Ollama on the laptop and pull. Pulling does not run the model, so the CPU-only machine is fine for this.

ollama pull qwen3:8b
ollama pull qwen3:14b

# then copy the whole model store into the staging folder
xcopy /E /I "%USERPROFILE%\.ollama\models" "transfer\ollama-models"

Copying Ollama's own store, rather than downloading a raw GGUF, is deliberate: the store carries each model's chat template and stop tokens alongside the weights. Hand-writing those in a Modelfile is easy to get subtly wrong, and a wrong chat template reads as "the model is bad" rather than as a config error.

B · Retrieval models, from Hugging Face

pip install -U "huggingface_hub[cli]"

huggingface-cli download BAAI/bge-m3 \
  --local-dir transfer\models\bge-m3
huggingface-cli download BAAI/bge-reranker-v2-m3 \
  --local-dir transfer\models\bge-reranker-v2-m3

--local-dir matters. Without it the files land in Hugging Face's cache as symlinks into a blob store, and symlinks do not survive a copy through a shared folder — you arrive with a folder of broken shortcuts. This flag writes real files.

C · Python packages, as wheels

Both machines are Windows on Python 3.13, so wheels downloaded here install there.

pip download -r backend\requirements.txt -d transfer\wheels --only-binary=:all:
pip download pymupdf -d transfer\wheels --only-binary=:all:

# phase 03 onward — bulky, but you do not want a second trip
pip download torch --index-url https://download.pytorch.org/whl/cu124 ^
  -d transfer\wheels --only-binary=:all:
pip download sentence-transformers qdrant-client fastapi "uvicorn[standard]" ^
  python-multipart sse-starlette -d transfer\wheels --only-binary=:all:

--only-binary=:all: is the safety catch. Without it pip may quietly fetch a source archive, which then needs a C compiler on the workstation to build — a failure that only appears at the worst moment. With it, pip fails here instead, where you can do something about it.

D · The repository itself

Ordinarily a git pull. With no network on the far side, clone or export to transfer\repo and copy it across, or keep a USB git remote in the shared folder and pull from that.

And two lines in backend\.env, because after the transfer these are folders on disk, not names to look up online:

HBL_EMBEDDING_MODEL=storage/models/bge-m3
HBL_RERANKER_MODEL=storage/models/bge-reranker-v2-m3
HBL_HF_OFFLINE=true

storage\ and wheels\ are both gitignored, so nothing here can reach the repository.

03Making it feel fast

The card is a 4060 Ti at 288 GB/s of memory bandwidth, which is the number that actually governs speed. Three changes matter, and the first is free.

Turn off Qwen3's thinking

Qwen3 is a reasoning model: by default it writes a <think> block before answering — often several hundred tokens the reader never sees, every one of them sitting in front of the first visible word. For grounded summarising of retrieved policy text, it buys very little and costs the whole impression of speed. Already off by default in the config (HBL_LLM_THINK=false). This is the single largest win available.

Bench 8B against 14B before committing

ModelIn VRAMRough speedVerdict
qwen3:14b Q4~9 GB~20–25 tok/sReadable, noticeably slower than a hosted chatbot
qwen3:8b Q4~5 GB~35–45 tok/sFeels normal

Estimates, not measurements — the real numbers come from that machine. The reason to carry both across is that this is the one question the laptop cannot answer, and a second transfer trip to fetch the 5 GB you skipped is a bad trade. The corpus work here is extraction and faithful summarising rather than open-ended reasoning, which is exactly where a smaller model gives up least.

Watch prefill, not tokens per second

What makes a local chatbot feel slow is almost never the typing speed — it is the pause before the first word. Eight retrieved chunks is roughly 3–4k tokens the model must read before it may write anything, and on this card that is seconds. Two knobs, both already in the config: HBL_RETRIEVAL_RERANK_CANDIDATES caps how many passages the cross-encoder scores (60 → 30 is close to free, since fusion has already ranked them), and HBL_RETRIEVAL_RERANK_TOP_K controls how much text reaches the model at all. Tune these against real questions in Phase 08 rather than guessing now.

Both models fit alongside everything else

With the 8B chosen, the resident set is roughly 5 GB of LLM plus 2 GB of KV cache, 2.3 GB of embedder and 2.3 GB of reranker — about 12 of 16 GB, comfortable. The 14B pushes it to ~15.6 GB, which works but leaves no headroom. Ingestion is a separate matter: it runs offline, on its own, so the OCR model never has to share.

04What air-gap costs the OCR bench-off

This is where the constraint bites hardest, and it changes the order of the comparison.

Docling, MinerU and Surya each fetch their own layout and recognition weights the first time they run. On a machine with no network that is not a slow start, it is a failure — and pre-staging them means finding each engine's model repository by hand and pointing a cache environment variable at it. Doable, but it is real work per engine, and it has to be redone for each one that turns out to be a dead end.

Against that, qwen2.5vl:7b is already sitting on the workstation, runs through the Ollama server that is already there for generation, and needs no package and no weights at all.

So: bench the VLM first

It is the only candidate that costs nothing to try, and if its output on your five pages is good enough, the other three never need to be transferred. If it is not good enough, Docling is the one worth the staging effort — its table structure is the reason it is on the list. MinerU and Surya stay on the shelf unless both disappoint.
