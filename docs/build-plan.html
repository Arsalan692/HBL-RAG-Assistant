01Constraints this plan is built around

Five facts shape every decision below. All five are now confirmed; they are recorded here so later phases do not quietly re-open them.

Split development and execution

You build here on a CPU-only laptop and move the code to the office GPU box whenever something needs to actually run. That is a real architectural constraint, not a logistics detail: no absolute paths, no machine-specific assumptions, every model name in .env, and a headless CLI for every heavy operation so ingestion can run on the GPU box without a browser. Transfer is a git pull plus pip install -r requirements.txt, never a manual reconciliation.

Nothing leaves the building

Confirmed: this data may not touch a cloud API. Every model in the stack — OCR, embedding, reranking, generation — runs locally on the office GPU workstation. No hosted inference, no telemetry, no external calls at query time.

The provider interfaces stay regardless. Not as a route back to cloud, but because a fully local stack changes models far more often than a hosted one does: you will swap OCR engines during the Phase 01 bench-off, and you will re-pick the generation model once we know the workstation's VRAM. Each of those needs to be a config change rather than a refactor.

One practical consequence: model weights have to get onto the GPU host somehow. If that machine has internet access, the libraries fetch them on first run. If it is genuinely air-gapped, we pre-download every model to a local cache and copy it across — worth confirming early, because discovering it during Phase 01 stalls the bench-off.

Documents are heterogeneous at the page level

Some files are fully digital, some are complete scans, and some are mixed — a typed policy with a scanned annexure, or a single page of typed text with a photographed table dropped into it. Classification therefore happens per page, never per file. Section 02 covers this.

Answers carry legal weight

This is compliance material. A fluent, confident, wrong answer about a KYC threshold or a sanctions obligation is worse than no answer. Every response cites document, page and section, and the system refuses rather than guesses when retrieval comes back thin.

The corpus mutates

Adding and deleting documents is a first-class operation, not an afterthought. Deletion has to be total — vectors, keyword index, registry row, cached page images, parsed markdown — with no orphaned fragments that keep surfacing in answers.

02The mixed-page problem, solved properly

This is the part most RAG tutorials get wrong, and the part your corpus will punish hardest. A file-level "is this scanned?" check fails the moment one PDF contains both kinds of page.

Every page is probed independently with PyMuPDF and scored on three signals before any extraction happens:

  • Character yield — how much extractable text the page's text layer actually returns.
  • Raster coverage — the fraction of page area occupied by embedded images.
  • Text sanity — a garble score. Some scanned documents already carry a bad text layer baked in by an office scanner. It looks like text to the extractor and reads like noise to the model, so a page whose text layer is mostly broken ligatures and stray glyphs is forced down the OCR path regardless of character count.

Everything converges on one human-readable artefact per document: a markdown file with page markers, plus a provenance record noting which method handled each page and how confident it was. That file is your quality gate. You open it, you read it, and you can see immediately whether a scanned annexure came through clean or came through as soup — before a single vector has been computed.

Tables

Tables are extracted to markdown and wrapped in atomic markers so the chunker can never split one across a boundary. Half a table is worse than no table: the model reads the surviving rows as the complete picture and answers accordingly. Where a table is too large to keep whole, it is repeated with its header row in each part and labelled as continued.

03Architecture

Three independent subsystems over shared storage. Ingestion is offline and slow; retrieval and generation are online and fast. Keeping them separate is what lets ingestion run on the GPU box overnight while you develop the UI on the laptop.

Two teals, on purpose

White text on the brand teal #009F8C measures 3.31:1, under the 4.5:1 that WCAG AA asks for body text. Rather than distort the brand colour, the theme carries two tokens: --hbl-green is the true brand teal and is used only where nothing sits on top of it — borders, focus rings, progress bars, the streaming caret, the mark itself — while --hbl-solid is a deeper step used for anything carrying text or an icon. In dark mode the relationship inverts: the fill stays bright and the text on it goes near-black. Measured in the browser: 4.67:1 light, 10.47:1 dark.

What the design implied that the plan didn't

The sidebar reads New Chat · History · Saved · Documents · Settings, and the account menu ends in Sign Out. Those are features, not decoration. Chat history and saved answers are still to build; sign-in has been explicitly deferred until the core works.

The reverse was also true: the showcase had no screen for uploading a document, no ingestion progress and no delete confirmation, even though those are core requirements. They remain to be designed, in Phase 07's second pass.

Fitting three models into 16 GB

Answering one question uses three different models at once. All three have to be in GPU memory together, so they need a budget:

ModelJobMemoryNote
Qwen3-14B (4-bit)Writes the answer~9 GBPlus ~2 GB of working memory for a 16k-token context window.
bge-m3Turns text into vectors~2.3 GBOnly model needed during ingestion, so it gets the whole card to itself then.
bge-reranker-v2-m3Re-sorts search results~2.3 GBRuns on ~30 short passages per question. Fast.
Total~15.6 GBTight against 16 GB. Two escape hatches below.

If that runs out of memory in practice, we take one of two steps, in this order: convert the two small models to 8-bit, which roughly halves them and costs almost no accuracy; or drop the answering model to 8B, which frees about 4 GB but is a real quality loss on policy reasoning. We try the first before the second.

One honest caveat about this card. The 4060 Ti has plenty of memory but fairly slow memory speed compared to bigger cards. That doesn't affect answer quality at all — it affects how fast words appear. Expect roughly 20–25 words per second from the 14B model, which reads as comfortable in a streaming chat window but is not instant. Ingestion is unaffected; that work is a one-time overnight job either way.

On frameworks — why no LangChain

The obvious question, and worth answering explicitly rather than by omission. LangChain is excellent at what it is for: assembling a working RAG baseline out of standard parts in an afternoon. The difficulty is that almost none of this project's actual work is standard parts.

What we needWhat the framework offersResult
Per-page scanned/digital/hybrid routingLoaders that return page textWritten from scratch either way
Section-aware chunking, atomic tablesCharacter and token splittersWritten from scratch either way
Persistent BM25 that deletes with the documentBM25Retriever — in-memory, rebuilt from the full corpus, no deletionActively wrong for the requirement
Total, verifiable document deletionInconsistent delete() support across store wrappersDrop to the Qdrant client anyway
Per-stage retrieval scores for tuningComposed retrievers with scores buried mid-chainFighting the abstraction during the phase that matters most

So the framework would carry roughly the last twenty percent of the pipeline — the part that is already a thin call to Qdrant or a cross-encoder — while the eighty percent that is genuinely hard sits outside it. That trade is worth taking when the alternative is a lot of code. Here the orchestration it replaces is a few hundred lines, and in exchange it adds a large dependency tree, a fast-moving API, and a layer between you and the retrieval scores exactly when you need to see them.

Decided: no framework. We call the same libraries LangChain would have called — PyMuPDF, the Qdrant client, sentence-transformers, SQLite FTS5, Ollama. Fewer moving parts, and full visibility into the retrieval scores during the phase where that visibility is worth the most.

The contract the backend has to satisfy

Because the interface was built first, the response shape is already fixed. Two files in frontend/src/ define it, and matching them means no component needs changing when the mock data is swapped out:

  • types.ts — Source, Message, ChatSummary. These mirror the API responses field for field.
  • data/mock.ts — the canned content to replace. Everything the UI currently renders comes from here.

Three details are easy to miss and expensive to get wrong:

  • Answers are markdown, and citations are literal [1], [2] tokens inside the prose. The renderer swaps those for clickable pills at display time. The generation prompt has to emit exactly that form, or citations render as plain bracketed numbers.
  • Sources must arrive before the answer text. The stream sends retrieval results first so the pills can resolve while the prose is still being written. The retrieval stepper also wants a document count and a source count.
  • GFM tables are rendered and styled — the model may emit them freely, which matters for a corpus this table-heavy.

The simulated stream lives in frontend/src/App.tsx. Replacing it with a real SSE reader is the only frontend change Phase 06 requires; the component tree does not move.

Environment note — superseded

An earlier revision of this plan called for rebuilding on Python 3.12, on the grounds that a few OCR engines — the PaddleOCR family in particular — don't publish 3.13 wheels. That was overruled: the project stays on Python 3.13.5, the version already installed.

The cost is accepted and narrow. PaddleOCR simply drops out of the Phase 01 bench-off, leaving Docling, MinerU, Surya and a local vision model — four candidates, which is plenty. If every one of them disappoints on your scans, installing 3.12 alongside is still a five-minute fallback rather than a rewrite.

04Phases

Sequential, because each phase consumes the previous one's output. Phases marked Gate stop and wait for you — those are the points where a bad result is cheap to fix and expensive to discover later.

One exception has already happened: Phase 07 was pulled forward and the interface built against mock data before any of the backend existed. That was worth doing — it settled the shape of an answer, and the citation format in particular, while changing it was still free. The rest of the sequence stands.

00Built

Skeleton, config and provider contracts

A backend/ package on the existing Python 3.13 environment; pydantic-settings configuration driven entirely by .env; structured logging; and the four provider protocols — LLM, Embedder, Reranker, OCR — that every later phase codes against. A cli entry point that all heavy operations hang off, so ingestion can run headless on the GPU box.

The interfaces earn their place even without a cloud fallback: the OCR engine is chosen by bench-off in Phase 01, and the generation model may be re-picked if the VRAM budget bites. Both need to be a config change.

Built. Two decisions in the implementation are worth recording. First, the registry stores a description of each provider — an import target and the modules it needs — and checks availability with importlib.util.find_spec rather than importing. That is what lets health run on the laptop, where torch is not installed and never will be; a test asserts that reporting status imports nothing. Second, HBL_LLM_BASE_URL is validated to resolve to loopback or the local network, so a mistyped .env cannot point the corpus at a public endpoint. The offline rule is enforced at the one place a URL enters the system, not left to discipline.

Only the Ollama provider is real. The embedder, reranker and the four OCR candidates are registered with the phase that implements them, so asking to load one fails with a sentence naming that phase instead of an ImportError for a module nobody wrote.

01Gate

Parsing: page router, OCR, tables

The page classifier from Section 02, all three extraction routes, the hybrid merge, table extraction to markdown, and per-document output with provenance. Then a bench-off: the same five pages — one clean digital, one full scan, one mixed, one dense table, one poor-quality scan — run through each OCR candidate, output placed side by side.

This phase is roughly a third of the project's real difficulty. Everything downstream is cheap to redo; bad parsing is invisible and poisons every answer.

GateYou read the generated markdown for a fully scanned policy and a mixed one, and confirm the tables are legible and the text is clean. Nothing proceeds until you do.
02Chunking

Structure-aware splitting and metadata

Policy documents are hierarchies — 4., 4.1, 4.1.2 — so splits follow section boundaries, detected from numbering patterns plus font-weight and size heuristics. Target ~700 tokens with ~120 overlap, tables atomic. Every chunk carries doc_id, title, year, section breadcrumb and page number; those fields become the citation the user sees.

Done whenA chunk dump shows correct section breadcrumbs, no table split across a boundary, and no chunk that begins mid-sentence with no context.
03Storage

Index, registry, and true deletion

Qdrant collection with payload indexes; a SQLite registry holding one row per document with its SHA-256, page count, chunk count, status and timestamps; FTS5 for keyword search in the same database. Ingestion runs as a background job with real status transitions — queued → parsing → ocr → embedding → ready or failed — because a 60-page scanned PDF takes minutes and the UI needs something honest to show.

The SHA-256 catches exact re-uploads, which your corpus already contains: two copies of the AML/CFT/KYC policy at identical size, and a duplicated Compliance Program file.

Done whenIngest three documents, delete one, and confirm by query that not one fragment of it can be retrieved — vectors, keyword hits, cached page images and parsed markdown all gone.
04Retrieval

Hybrid search with reranking

Dense top-30 and BM25 top-30, fused with reciprocal rank fusion, reranked by cross-encoder, cut to top-8. Hybrid is not optional here: semantic search alone reliably misses exact identifiers, and your corpus is built on them — A-INST-2025-01, CDD, EDD, STR, PEP, threshold figures, clause numbers. A curated acronym glossary expands queries before search so "CDD" and "customer due diligence" reach the same passages.

Done whenThe evaluation harness reports recall@8 against the golden set, with an ablation table showing vector-only, hybrid, and hybrid-plus-rerank side by side.
05Answering

Grounded generation with citations

Numbered context blocks, a strict citation contract, and explicit refusal when retrieval is weak. Follow-up questions are rewritten into standalone queries before search, so "what about for corporate customers?" resolves against the previous turn. Responses stream token by token. Where two retrieved chunks come from different vintages of the same policy, the newer is preferred and the conflict is stated rather than silently resolved.

Done whenEvery answer names document, page and section; and a question the corpus genuinely doesn't cover is refused cleanly instead of being improvised.
06API

FastAPI service

Chat with SSE streaming; document upload returning a job id; document list with live status; delete; a page-image endpoint that powers citation previews; health. Typed request and response models throughout, so the UI is generated against a contract rather than guesses.

Done whenThe complete upload → ingest → ask → cite → delete cycle runs from the interactive API docs with no UI present.

05The versioning hazard in your corpus

Worth calling out separately, because it is already present in the file list you showed me and it produces the most dangerous class of failure this system can have.

Several policies appear more than once, in more than one vintage:

  • Global AML CFT CPF and KYC Policy – 2023 alongside the 2025 A-INST-2025-01 enclosure of the same policy.
  • Sanctions Compliance Policy – 2023 alongside its 2025 enclosure.
  • Compliance Risk Policy & Program alongside Compliance Risk Policy 2023 – Portal Version (2).
  • Two byte-identical copies of the AML/KYC enclosure, and a duplicated Compliance Program file.

Ask a threshold question and the retriever may return the superseded 2023 clause. The model has no way to know it is stale, and if both vintages surface it reads them as corroboration — producing an answer that is more confident precisely because it is drawing on an obsolete source. Nothing about the output looks wrong.

The treatment runs across three phases: SHA-256 deduplication at ingest removes the exact copies; a policy_family and year pair is extracted from filename and cover page at chunking; and at answer time the newer vintage is preferred, with any genuine disagreement surfaced to the reader rather than resolved silently. The library UI also marks superseded documents so a user can see the corpus contains both.
